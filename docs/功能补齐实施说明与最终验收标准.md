### 0.3 剩余修复清单

下面“静态缺口”指读取源码发现实现与目标不符，不代表已经执行失败复现；“待复现风险”必须先构造测试确认，再做最小修复。优先级按可能造成的事故评估：P0 是重复下单、重复累加、错误解除阻断、错报零写入等数据安全问题；P1 是阻塞操作、无法恢复或错误状态等主要功能问题。

#### R01 · P0：文件锁所有权、重入和异常清理（静态缺口）

- **定位：** `app/wps_atomicio.py` 的 `FileLock.acquire/release`，`app/sss_journal.py` 的批次锁和 journal 数据锁。
- **问题：** 重入计数属于路径/线程，但文件描述符和线程锁属于实例；`release()` 在计数大于 1 时不清理当前实例的持锁标记，重复释放可错减其它持有者的计数。无锁原语引发的 `RuntimeError` 不在现有 `OSError` 清理路径内。路径字符串未统一，别名也可能绕过进程内互斥。
- **修改方向：** 明确支持的同实例和多实例重入规则，统一持有状态及资源所有权，保证配对释放、重复释放幂等和所有异常释放；规范化锁路径并验证符号链接/大小写别名的行为。批次执行锁与短时数据锁应有明确锁顺序，不能依赖未验证的重入巧合。
- **验收：** A21、A33。当前提交线程先 prepare、再并发 POST、最后 finalize，不能未经复现就宣称“worker 写日志导致死锁”；必须沿真实调用链验证完整批次不会自锁，且其它进程拿不到仍被持有的锁。

#### R02 · P0：闪时送取锁后重读权威阻断状态（静态缺口）

- **定位：** `app/sss.py` 的 `blocking_state` 与 `_begin_submission()`。
- **问题：** 先读取阻断状态，随后才取批次锁；取得锁后沿用先前缓存结果。两个进程先后运行时，后来者可能漏掉先执行者刚留下的未决记录。
- **修改方向：** 在提交锁内重新读取并校验 journal、日期、账号和 origin；锁失败、状态改变或读取失败立即拒绝，不发创建订单请求。保持普通下单发现既有阻断时不登录的行为。
- **验收：** A22、A33。两个独立进程用 barrier 控制“先读空日志—另一进程留下未决—再取锁”，后来者 POST 数必须为 0。

#### R03 · P1：未决记录不能因当前筛选条件而失去处置入口（静态缺口）

- **定位：** `app/bridge.py:sss_uncertain_records`、`app/sss_review.py:_scope_records/pending_views` 及前端未决列表。
- **问题：** 当前日期/账号/origin 过滤能避免跨平台误处置，但也可能隐藏仍造成阻断的跨作用域记录；历史未决记录也需要可发现的入口。
- **修改方向：** 分别展示“当前范围”“造成当前阻断的其它范围”“历史未决”的脱敏计数和列表，提供切回原作用域核对的明确路径。查看其它范围不等于授权当前平台处置；缺失旧凭据时保持阻断并提示人工处理。
- **验收：** A23。切换来源、账号、平台或日期后记录不消失、不自动解除，且能从界面找到正确处置路径。

#### R04 · P0：核对证据与人工处置必须原子校验（静态缺口）

- **定位：** `app/sss_review.py:start_review/_fresh_snapshot/resolve_records`、`app/bridge.py:sss_uncertain_resolve`。
- **问题：** 指纹校验与关闭记录分开取锁，存在检查与使用之间的竞争；网络核对结束后重新计算日志指纹，可能把核对期间的外部变更误当成已覆盖证据。人工处置还需纳入统一协调器。
- **修改方向：** 固定查询前记录集合/版本，查询后验证覆盖关系；将当前指纹、记录状态、作用域、证据新鲜度校验及状态变更放到同一锁内。自动确认造成的本次合法变更与外部变更须区分；提交、核对、处置互斥。重复处置不再写账，也不影响新记录。
- **验收：** A24。核对中、检查后处置前插入或改变记录，旧证据必须拒绝；两个进程并发处置不得错误解除任何记录。

#### R05 · P0：不能仅凭目标时间窗缺失判定“站内没有”（待复现风险）

- **定位：** `app/sss_review.py:start_review`、`app/sss.py:_reconcile_tasks`，参考服务端 `app/ordering/uncertain.py`。
- **问题：** 当前直接按 confirmed/missing 分类，需证明是否能识别相似订单、误日订单及不完整分页；`station_found_other_day` 分支是否真正可达也需验证。
- **修改方向：** 目标窗缺失后按业务规则扩大只读搜索范围；保留日期/字段不同或身份歧义，不把它们当成可以重发。扫描失败、分页截断、响应不完整、时间窗接口不支持时必须有明确分类和安全回退。
- **验收：** A25。错一天、跨午夜、相似客户、重复匹配和缺页均不能误形成允许重发的 `station_missing`。

#### R06 · P0：多张表同批写入的账本基线（待复现风险）

- **定位：** `app/wps_cloud.py:build_plan/_guard_block_reason/_apply_plan_locked`。
- **问题：** 多份 plan 可能绑定同一个初始 `ledger_digest`，第一张表完成并记账后，后续表可能被自己引起的变化误判为预览过期。不能用只测单表的结果证明批量功能正常。
- **修改方向：** 锁内验证整批起始基线，逐表推进本次操作的合法账本版本，同时拒绝外部变更；保留同日期同目标的未处置/防重复闸门，并排除当前 operation 的自锁。
- **验收：** A26、A33。用产品实际配置的多表批次（至少六表夹具）验证首次、重复、部分失败和重启恢复，不因本批合法记账误拒绝后续表。

#### R07 · P0：WPS 恢复与上传跨进程互斥（静态缺口）

- **定位：** `app/wps_recovery.py:resolve_pending_operation` 与 `app/wps_cloud.py` 上传操作锁。
- **问题：** 恢复的账本合并有数据锁，但整个“读状态—核对—记账—保存 journal”缺少与上传共享的操作级互斥保证。
- **修改方向：** 恢复与上传使用一致的操作锁/锁顺序，取锁后重载权威状态，校验版本后提交；两个恢复者重复执行保持幂等。恢复只读云端，不得顺便补写云端。
- **验收：** A27、A33。并发上传与恢复、两个恢复者、账本合并成功但 journal 保存失败后重启，均不重复累加/记账，不丢闸门。

#### R08 · P1：所有操作异常都释放占位，结果不得假成功（静态缺口）

- **定位：** `app/bridge.py:start_order/start_sss/wps_authorize/check_updates/sss_day_orders/wps_check_copies` 和 `app/operations.py`。
- **问题：** reserve 后的配置保存、密码保存、线程创建/启动失败需要完整释放；授权/更新的失败终态和只读入口并发策略需统一，不能仅靠 `worker_alive()`。
- **修改方向：** 从 reserve 起统一管理生命周期；失败不覆盖已有 operation，不保留僵尸 busy；定义只读入口是否共享登录/浏览器状态、可否并发，必要时纳入协调器。更新检查的正常“无更新”与检查异常要区分。
- **验收：** A28。逐个异常注入后状态真实、占位释放，下一个安全操作可启动；冲突立即返回且不影响原任务。

#### R09 · P1：预览中的本地 SHA 必须在上传时实际校验（静态缺口）

- **定位：** `app/wps_preview.py:PreviewRecord.local_sha256`、`app/bridge.py:wps_preview/_wps_upload_impl`。
- **问题：** 预览保存了 SHA，上传当前主要比对 context/plan；只改样式或非业务内容，业务计划可能不变，仍可能使用旧令牌。
- **修改方向：** 上传显式重算文件 SHA 并绑定已解析数据；避免 hash/读取之间被修改形成混合快照（例如读入固定字节快照再解析）。文件路径、内容、配置、日期、云端基线改变均作废令牌。
- **验收：** A29。只改格式或无关 sheet、同大小且恢复 mtime 的修改、解析中替换文件，旧令牌都必须零写入拒绝。

#### R10 · P0：插入行异常不能直接报告零写入（静态缺口）

- **定位：** `app/wps_cloud.py` 的 `insert_rows` 异常分支及 rollback 判定。
- **问题：** 服务端已插入而客户端超时，也会进入“插入失败”；未经回读证明不能记 `failed_no_write` / `cloud_writes=0`。
- **修改方向：** 在插入前落盘意图；异常后只读核对结构，不能判定则进入 `uncertain` 保留闸门。安全回滚必须证明行身份和结构未被协作者改变，不能猜测删行。区分“从未写入”与“写过后完整回滚”，不把后者标成 `proven_no_write=true`。
- **验收：** A30、A33。模拟服务端插入成功后客户端抛异常、回读失败及协作者插入/排序；不误删、不释放闸门、不假报零写入。

#### R11 · P1：新增界面必须有交互端到端覆盖（覆盖缺口）

- **定位：** `frontend/src/components/CloudForm.tsx`、`TaskPanel.tsx`、`hooks/useApp.tsx`。
- **问题：** 上轮前端测试通过不代表新业务界面经过组件或浏览器验证。
- **修改方向：** 为预览—上传—恢复、未决—核对—确认、验证码/停止/重连建立交互测试，使用契约一致的 Bridge 模拟，再进行真实桌面冒烟；按钮禁用只提供体验，后端仍权威判断。
- **验收：** A31。双击不重复调用危险动作；部分成功和未知不显示绿色完成；刷新后从 Bridge 恢复状态，过期证据不能处置。

#### R12 · P1：恢复查询依赖隔离和敏感信息边界（待复现风险）

- **定位：** `app/bridge.py:wps_recovery_status`、`app/wps_recovery.py:recovery_status`，所有新日志/快照和错误输出。
- **问题：** Bridge 获取账本后调用恢复查询时需确认是否传入同一实例，不能让底层默认加载真实用户目录，导致测试污染或查询不同账本。日志、界面与权威 journal 的脱敏规则也需分别定义。
- **修改方向：** 显式传递本次数据目录及账本；自动测试完全隔离 HOME/XDG/用户配置、凭据及网络。UI 必要业务名单可按原流程显示，未决列表和日志应脱敏；journal 内核对必需的完整身份信息仅能留在受保护本地文件，禁止提交/导出到测试证据。
- **验收：** A32。哨兵真实目录在自动测试中访问次数为 0；错误、事件、快照、报告不泄露秘密；缺少密钥链时不回退明文存密码。

## 1. 总体原则

### 1.1 必须保留桌面端特性

补齐功能不能破坏以下既有能力：

- Windows、macOS、Linux 三个平台运行；
- `pywebview` 桌面窗口和现有 React 前端；
- 内置 Chromium、Playwright fallback 和浏览器自动化；
- Windows Credential Manager、macOS Keychain、Linux SecretService 等系统密钥链；
- 桌面端更新器、平台安装包选择、更新失败回滚；
- 原有管理后台订单处理流程和 Excel 读写行为。

### 1.2 不移植服务端专属功能

以下能力不属于桌面端补齐范围，不能为了“与服务端文件一致”而引入：

- 网页账号注册、审批、邀请码和角色权限；
- Android、Kotlin、Chaquopy、Termux；
- Cloudflare Tunnel、服务端 Web API、后台数据库；
- 手机端浮动日志按钮、移动端软键盘布局；
- 服务端专属的管理员认证流程。

桌面端是单用户本机应用，可以没有服务端角色权限，但仍必须有明确确认、审计备注、作用域校验和失败关闭。

### 1.3 安全优先级

两类事故必须优先防止：

1. 闪时送重复下单，导致客户收到多份餐；
2. WPS 云端餐次重复累加、覆盖协作者的 `0` 或错误写入正式表。

任何无法确认的远端写入结果，都必须进入“未知/未决/恢复中”状态，不能自动重试、不能把未知当失败、不能静默清除本地记录。

## 2. 本次需要修改的功能方向

### 2.1 P0：WPS 云文档同步数据正确性

主要文件：

```text
app/wps_cloud.py
app/bridge.py
app/wps_preview.py
app/wps_journal.py
app/wps_recovery.py
app/wps_summary.py
```

#### 2.1.1 总餐次必须按增量累加

正确公式：

```text
本批增量 = 本地本批餐次 - 账本已记录的本批餐次
云端新总餐次 = 云端当前总餐次 + 本批增量
```

必须满足：

- 云端原值为 `5`，本地本批为 `6`，首次上传后为 `11`；
- 相同本地表重复上传，增量为 `0`，不能再次加餐；
- 本地餐次减少时不能负向修改云端，必须给出人工核对警告；
- 账本按日期、目标表、客户、电话和行槽位记录；
- 只有云端写入并回读校验成功后才能更新账本；
- 账本损坏、不可读或结构不支持时必须阻断写入。

#### 2.1.2 日期格必须保护协作者写入

日期格处理规则：

| 云端原值 | 允许动作 |
|---|---|
| 空值 | 写入 `1` |
| `1` | 保持 `1`，不重复写入 |
| `0` | 保持原值，不覆盖 |
| 其它非空值 | 保持原值，不覆盖，并加入警告 |

回读校验必须确认：

- 本程序写入的空值确实变为 `1`；
- 已有非空值没有被覆盖；
- 校验不一致时不能更新账本，也不能报告整张表成功。

#### 2.1.3 同一客户多行必须按槽位处理

不能只使用 `(姓名, 电话) -> 行号`。必须支持：

```text
(姓名, 电话, slot=1) -> 第 1 行
(姓名, 电话, slot=2) -> 第 2 行
```

每一行必须独立处理：日期格、总餐次、已出餐公式、剩余公式、通讯记号和账本条目不能串行覆盖。

#### 2.1.4 批次日期不匹配必须整批零写入

下列情况必须在任何云端写入前阻断：

- 本地表目标日期与当前 WPS 目标日期不一致；
- 日期列缺失或日期无法可靠解析；
- 星期标记与目标日期不一致；
- 目标表配置不完整或指向过期目标；
- 测试模式未配置测试副本。

阻断结果必须明确报告：

```text
cloud_writes = 0
ledger_updates = 0
proven_no_write = true
```

并且被阻断的表不能发送任何读取或写入请求（除非该读取是前置配置检查明确允许的只读操作）。

#### 2.1.5 新客户、排序和失败回滚

必须保留以下执行语义：

1. 新客户先插入统一位置；
2. 写入姓名、地址、电话、类型、餐种和格式；
3. 排序前失败，仅在能证明本次新行身份且无协作结构变化时允许回滚删除，否则保留 `uncertain`；
4. 排序成功后再失败，不能猜测删除行，必须进入 `uncertain`；
5. 排序辅助列删除失败时必须告警并保留恢复信息；
6. 排序后必须重新按姓名+电话+槽位定位行号，不能继续使用旧行号。

#### 2.1.6 预览与上传必须分离

`wps_preview()` 必须是只读操作，不能写云端、不能更新账本、不能创建意图日志中的执行记录。

成功预览必须生成：

- `preview_id`；
- 过期时间，默认 600 秒；
- 本地 Excel 文件指纹；
- 目标表和配置上下文指纹；
- 计划指纹；
- 逐表计划、警告、阻断原因；
- 独立的 `planned_summary` 和 `execution_summary`。

`wps_upload(preview_id)` 必须：

- 拒绝空的 `preview_id`；
- 拒绝不存在、过期、已消费、已作废的预览令牌；
- 上传前重新计算本地文件、目标表、日期、排序、地址顺序和计划指纹；
- 任意指纹变化都必须在云端写入前拒绝；
- 令牌只能消费一次；进入真实执行后，即使超时或部分失败也不能复用，必须走恢复或重新预览；
- 云同步关闭后立即作废所有未使用令牌；
- 写入前的拒绝路径必须证明没有云端写入；开始执行后的错误不能伪装成这种拒绝，应报告已写入/部分成功/未知并保留恢复信息。

#### 2.1.7 WPS journal 与恢复

每次真实上传必须在云端写入前落盘意图日志，至少记录：

- operation id；
- 目标文件、子表、worksheet id、目标日期和日期列；
- 客户、电话、槽位；
- 写入前原值；
- 期望值；
- 账本条目；
- 每张表的状态和最后更新时间。

状态至少包括：

```text
planned
writing
ledger_pending
uncertain
verified
failed_no_write
not_started
retired_guarded
```

恢复入口要求：

- `wps_recovery_status()` 只读本地日志，不联网、不写文件；
- `cloud_verified` 必须重新只读云端并证明所有期望值成立；
- `cloud_untouched` 必须重新只读云端并证明仍与写入前基线一致；
- `retire_guarded` 只能退出全局待处理队列，不能解除同日期+同目标表的防重复闸门；
- `keep` 必须保持阻断；
- 恢复入口永远不能写云端；
- 重复处置必须幂等；
- 账本合并失败必须进入 `ledger_pending`，不能假装完成。

### 2.2 P0：闪时送未决订单安全机制

主要文件：

```text
app/sss.py
app/sss_journal.py
app/sss_review.py
app/sss_url.py
app/api_client.py
app/bridge.py
```

#### 2.2.1 权威 journal 和阻断键

未决日志必须是跨重启、跨名单来源、跨窗口有效的权威状态。

批次阻断键为：

```text
送达日期 | 规范化账号
```

名单来源 `wps/excel` 不能参与阻断键，切换来源不能解除阻断。

平台 origin 必须单独保存并规范化。账号或平台变化不能静默隐藏旧未决记录；同日期下的跨账号/跨平台未决记录必须继续阻断并要求人工处置。

#### 2.2.2 每个 POST 前必须写入意图

纯 HTTP 和 Playwright 两条路径都必须执行：

```text
写入 inflight
→ 发送 POST
→ 确定拒绝：discarded
→ 成功但未完成站内对账：unresolved
→ 超时、断线：unresolved；进程杀死来不及更新时保留 inflight，同样阻断
→ 站内只读确认已有订单：resolved
```

journal 写不下去时必须停止本批，不能发送 POST。

#### 2.2.3 journal 损坏必须失败关闭

以下情况不得当作“没有未决记录”：

- JSON 损坏；
- 文件不可读；
- 版本不支持；
- 记录缺少 journal id；
- 记录状态非法；
- 平台作用域无法规范化。

普通下单入口必须返回清晰错误，在登录前阻断，禁止创建订单和自动重试。明确发起的只读核对可以登录/查询，但不能把损坏日志视为空列表，不能基于不完整身份或证据解除阻断；无法安全读取时提示备份及人工修复，不擅自覆盖原文件。

#### 2.2.4 只读核对与人工处置

`start_sss_review()`：

- 只允许登录和查询订单；
- 不允许调用创建订单接口；
- 查询失败必须标为 `scan_failed`，不能当成站内没有；
- 核对结果必须保存快照、日志指纹、平台 origin 和过期时间；
- 自动确认站内已存在的订单可以标记 `resolved`。

`sss_uncertain_resolve()`：

- `station_present`：确认站内已有，解除对应记录阻断；
- `station_absent`：必须有新鲜完整核对证据，且所有选中记录均为 `station_missing`；
- `keep`：保持阻断，不创建订单；
- `confirm` 必须与 decision 完全一致；
- 非 `keep` 备注至少 4 个字符；
- 核对快照、当前日志、当前账号和当前平台 origin 不一致时必须拒绝；
- 处置入口本身不能发送任何创建订单请求。

#### 2.2.5 时间窗、并发和默认值

默认值对齐参考项目，并用当前代码及测试重新确认（参数一致不代表安全行为已经验证）：

- 闪时送最大并发：8；
- 读取请求默认超时：30 秒；
- 时间窗查询优先，服务端不支持时才回退全量扫描；
- 列表扫描需记录页数、耗时、命中数和是否启用预筛；
- 余额未知或预检失败时不能提交订单。

如果用户已有自定义并发或超时配置，默认值迁移不能覆盖用户显式设置。

## 3. 不允许的实现方式

以下行为一律视为验收失败：

- 用 `git reset --hard` 覆盖现有未提交工作；
- 直接把服务端 `app/` 或 `frontend/` 整体覆盖桌面端；
- 用内存字典代替闪时送权威 journal；
- POST 后才写 journal；
- journal 读失败时当作空列表继续下单；
- 用“请求超时”推断订单一定没有创建；
- 用 `retire_guarded` 解除 WPS 同目标表的重放闸门；
- 预览后不重新检查本地文件和云端计划就上传；
- 用前端禁用按钮代替 Bridge 后端安全校验；
- 在自动化测试中访问真实账号、真实订单、正式 WPS 写入目标；
- 把密码、验证码、token/cookie/签名等秘密写进普通配置、日志、核对快照、报告或测试输出；把未经脱敏的业务数据作为验收附件。

权威 journal 为核对所需而保存的完整业务身份信息不等于日志泄露，但必须限制本地访问、禁止提交 Git；UI 正常业务名单与错误输出/未决诊断列表应分别评估，不能为了脱敏破坏原有排单功能。

### 4.2 A21～A33 的具体执行方法

所有以下数据均为合成夹具，所有副作用在临时目录或受控测试服务执行。模拟服务器要记录实际收到/生效的写请求，不能只统计客户端返回值。用同步事件/barrier 控制竞争，不能单靠 `sleep` 碰运气；常规并发回归建议重复至少 20 轮，确定性窗口至少完整复现 1 轮。单进程 mock 不能代替明确要求的双进程和重启测试。

**A21 · 文件锁**
- 输入：临时锁文件、两个锁实例、两条线程、两个独立进程。
- 动作：同实例/多实例嵌套 acquire-release；重复 release；内层释放后外层仍持有；相对/绝对/符号链接路径别名；强制 `_open` 或锁原语失败；无原语路径。
- 断言：外层未释放时竞争者不能进入；释放/异常后竞争者可进入；无 fd/线程锁泄漏。Windows 分支模拟只证明分支逻辑，Windows 实机另行确认，不能用 Linux 成功代替。

**A22 · 取锁前后的 journal 变更**
- 输入：两个独立进程共享临时 journal，第二进程停在“已读空日志、尚未取锁”。
- 动作：第一进程提交并留下 unresolved 后释放锁，再放行第二进程；另测第一进程仍持锁时第二进程立即被拒绝。
- 断言：第二进程锁内发现未决，不发 POST、不抹掉第一进程记录；已有阻断正常路径不登录。证据附 barrier 阶段、记录 ID 和服务端 POST 计数。

**A23 · 未决范围可见性**
- 输入：同日期账号甲/乙、平台甲/乙及历史日期记录，各一条。
- 动作：切换筛选条件、名单来源，调用 Bridge 并查看前端；在平台乙尝试用乙平台证据处置甲平台记录。
- 断言：当前阻断来源与历史记录均可发现；错误范围拒绝，原范围提供安全核对入口；不改变权威记录状态。

**A24 · 核对证据竞争**
- 输入：一条旧未决及可完整查询的合成订单列表。
- 动作：查询中新增记录、查询中改变原记录、指纹校验后处置前由另一进程修改、双进程同时处置；分别核对有匹配和无匹配。
- 断言：外部变化使旧证据过期或明确限制到仍能证明的记录；未查询的新记录绝不被解除；自动确认的合法内部更新可审计；重复处置不重复计数。

**A25 · 宽窗及查询完整性**
- 输入：目标日缺失但邻日有相似订单、跨午夜送达、同名异号、同号异名、同一身份多条、接口忽略时间窗、重复页/漏页、分页中途异常。
- 动作：只读核对后尝试 `station_absent`。
- 断言：误日/相似/歧义保留待人工确认，扫描不完整标 `scan_failed`；只在完整覆盖且明确没有时允许人工确认。完整缺失成功样例也须通过，不能用“一律阻断”假修复。

**A26 · 六表批次**
- 输入：六张独立合成表，分别覆盖既有客户、新客户、多槽位、日期 `0`、日期 `1`、空日期；总餐次初始 `5`，本批 `6`。
- 动作：一次预览并上传全部，重新预览重复上传；另一次在第三表写入后回读失败，重启并恢复。
- 断言：正常首次全部可执行，适用槽位总餐次 `11`，重复仍 `11`；每表/每槽位独立记账，日期 `0` 保持不变；未知表阻断重放，其它表状态真实，不因本批记账误判后续表过期。

**A27 · WPS 并发恢复**
- 输入：一个有完整期望值和基线的 pending operation，两个独立进程共享临时 journal/ledger。
- 动作：恢复与上传竞争、两个恢复同时确认、恢复验证后另一进程改变版本、账本保存后 journal 保存抛异常。
- 断言：不能并行跨越检查/记账关键区，旧版本拒绝，重复确认幂等；重启继续恢复时不二次记账；恢复远端写请求数始终为 0。

**A28 · 操作异常释放**
- 输入：各 Bridge 入口和受控失败实现。
- 动作：分别令配置保存、密钥链保存、线程创建/启动、授权、更新检查、网络查询、journal 写入抛异常；另测试无更新正常结果。
- 断言：结构化错误或既有可控错误契约，operation 状态与实际一致；自己的占位释放，别人的任务不被终止；之后可发起安全操作。记录 `active/current/last` 及冲突返回。

**A29 · 文件 SHA 和预览**
- 输入：可解析的合成 Excel 及已生成的 preview_id。
- 动作：只改样式/无关 sheet；替换同大小文件并恢复 mtime；解析中修改文件；改配置/目标日期/云端基线。
- 断言：旧令牌被拒绝且服务端写次数、ledger 更新数均为 0；不得产生旧 hash 与新解析数据混合的有效预览；未修改情况下新令牌仍可正常上传。

**A30 · 不确定插入与回滚**
- 输入：模拟 WPS 服务，能够先成功插行再抛客户端超时。
- 动作：插行生效后异常；异常后回读不可用；协作者随后插行或排序；另测真正未发请求的失败。
- 断言：生效或无法证明时为 uncertain，不能 `proven_no_write=true`，不能报可信零写入；协作者行不被删除；只有确实未写入才可报告零写入。成功回滚另记“已恢复基线”，不得伪装从未写过。

**A31 · 前端和桌面交互**
- 输入：真实组件/浏览器页面、契约一致的 Bridge mock 和一次目标平台桌面运行。
- 动作：预览双击上传、部分失败恢复、未决核对/过期处置、取消验证码、停止、刷新/重连、重复事件。
- 断言：危险动作调用次数不重复，后端冲突有提示；验证码可完成/取消、停止后保守保留在途未知；旧证据按钮不可误用，重连不丢操作状态；保存脱敏截图或测试记录。

**A32 · 隔离与敏感数据**
- 输入：临时 HOME/XDG/配置目录；真实目录访问哨兵、外网请求拦截；合成密码、验证码、cookie、手机号作为 canary。
- 动作：跑新模块测试、调用 recovery_status；让外部异常文本包含 canary；模拟密钥链缺失。
- 断言：自动测试真实用户目录/真实凭据/外网访问均为 0；输出没有秘密，未决列表和手机号诊断脱敏；本地 journal 仅保存必要业务身份、不保存登录秘密；安装包不含用户数据。

**A33 · 真进程崩溃恢复**
- 输入：子进程、临时磁盘数据、可观察写入的模拟服务器；不能使用真实订单/正式表。
- 动作：分别在闪时送 intent 已落盘但未 POST、服务器已收 POST 未返回、POST 已返回未对账时杀进程；在 WPS planned、写入已生效未回读、云端已验证未记账、账本已存但 journal 未完成时杀进程，然后启动新进程。
- 断言：所有日志仍可读取，未知保守阻断；自动重启不重复 POST/累加；明确未发送可安全核对后恢复；账本已存时恢复不会再次记账。每个断点给出服务端计数和重启前后状态，不能只用抛异常代替 kill。

### 4.3 证据有效性与禁止虚假 PASS

- 每项至少记录测试函数/场景名称、命令、退出码、关键断言及结果；可在脱敏的独立验收报告中引用文件路径。
- `SKIP`、缺环境、仅静态阅读、仅 mock、未运行、无法复现不是 `PASS`；须说明覆盖层级。`N/A` 必须给出业务不适用理由并由负责人确认，不能用来豁免 P0 安全场景。
- 上轮 4 个 Python skip 必须逐条列出原因、影响和替代验证；前端 helper 测试不能代替 A31。
- 记录 Git HEAD、tracked 差异和新增实现/测试文件清单，给最终源码/依赖锁文件生成校验清单或等价只读快照；含未跟踪实现的工作区不能只记 `git diff`。只收集源码，不复制凭据或业务数据。
- 验收期间不得同时修改被验收代码。测试后代码/依赖/配置改变，受影响结果作废；绑定新的候选快照重验，不要求为此 commit 或建立分支。

## 5. 人工验收标准

自动化全绿后，验收 agent 还必须完成测试环境和当前使用平台检查。真实生产操作必须由业务负责人明确授权；没有授权时使用测试副本、模拟客户端、干跑或预检模式。**干跑只能证明零提交路径，不能代替真实接口协议、写入回读或服务端创建结果的集成验证。**

### 5.1 WPS 测试副本

- [ ] 配置测试副本，不得默认指向正式排单表。
- [ ] 预览可以显示目标日期、逐表变更、警告和阻断原因。
- [ ] 预览不会修改云端单元格、账本或执行 journal。
- [ ] 修改本地 Excel 后上传旧 `preview_id` 被拒绝。
- [ ] 预览令牌重复上传第二次被拒绝。
- [ ] 云端已有总餐次和日期格的测试用例结果符合 A01～A04。
- [ ] 人工制造一次排序后回读失败，恢复状态能显示为未知，不能自动重传。
- [ ] `cloud_verified`、`cloud_untouched`、`retire_guarded`、`keep` 的可用动作和结果符合本文定义。
- [ ] 恢复入口操作前后云端只发生读取，不发生写入。

### 5.2 闪时送测试环境

- [ ] 使用干跑、预检、模拟 API 或专用测试账号，不直接发送生产订单。
- [ ] 模拟 POST 超时，确认日志变为 `unresolved`。
- [ ] 再次启动同日期同账号任务，确认在登录/POST 前被阻断。
- [ ] 切换名单来源、重启程序、改变 Excel 路径后仍被阻断。
- [ ] 切换平台 URL 后，旧平台记录不能被当前平台的核对结果解除。
- [ ] 查询失败显示“无法判定”，不能显示“站内没有”。
- [ ] 只读核对不会调用创建订单接口。
- [ ] `station_present`、`station_absent`、`keep` 均需要正确确认文本和审计备注。
- [ ] 处理损坏的 journal 时页面显示修复提示，Bridge 不抛未处理异常。

### 5.3 桌面端和前端

- [ ] 订单处理运行时，WPS 上传、闪时送核对和更新入口按规则冲突拒绝。
- [ ] 操作异常后再次点击可以正常重试，不会永久卡在 busy。
- [ ] 前端刷新或事件重放后不会重复显示同一条关键事件。
- [ ] WPS 预览、上传、恢复和闪时送未决列表均能看到明确的下一步动作。
- [ ] 错误、日志、未决列表及验收证据不泄露密码/验证码/token/cookie，业务身份按对应展示场景脱敏；云文档定位信息仅在必要本地业务界面显示，不附带可访问凭据或签名链接。

### 5.4 目标平台与三平台发布冒烟

**本机投入使用：** 必须在用户实际使用的平台及架构运行一次最终候选版本；若只验收 Linux，则结论限定 Linux，不能写“三平台通过”。**三平台对外发布：** 下列三平台均须完成实测。

- [ ] Windows：配置目录、文件锁、密钥链、pywebview、内置 Chromium、更新器。
- [ ] macOS：配置目录、文件锁、Keychain、pywebview、内置 Chromium、更新器。
- [ ] Linux：配置目录、文件锁、SecretService 缺失时的降级、pywebview、内置 Chromium、更新器。

如果当前没有三种系统，验收报告必须明确写出哪些是静态检查、哪些是容器/模拟验证，不能声称三平台最终通过。

当前平台还应核对：实际用户配置的向前兼容、启动/退出/重启、可用的系统浏览器与 fallback、验证码交互、密钥链可用/缺失、数据路径和文件权限。测试要保留配置/账本/journal 的受保护备份，不复制密码到验收材料。

更新器至少验证平台/架构选包、校验失败不安装及不破坏现有用户数据。涉及真实安装/覆盖/回滚，应在已授权的隔离安装目录或测试机器执行，不能为了验收擅自更新用户当前在用程序；未覆盖的分发/更新范围明确排除在放行结论外。

### 5.5 受控真实集成与投产范围

| 能力 | 合格集成环境 | 必须验证 | 没有环境时 |
|---|---|---|---|
| WPS 写入 | 用户授权的测试副本，API/CLI 与实际环境一致 | 首次增量、重复上传、`0` 保护、多表、回读、只读恢复 | 该能力不能直接放行；模拟测试通过仍只是条件通过 |
| 闪时送创建 | 真实服务的沙箱或明确授权的专用测试账号/测试名单 | 实际请求/响应、成功后只读匹配、journal 关闭、重复启动防重、错误边界 | 该能力不能直接放行；dry-run/预检不足以放行创建订单 |
| 桌面运行 | 用户实际 OS/架构的最终候选程序 | 第 5.3/5.4 节交互、密钥链、锁及数据持久化 | 仅代码层面通过，不放行该平台 |

真实服务上的超时/崩溃/并发故障不必直接制造；这些破坏性用例由模拟服务承担。正常协议与持久化闭环则在受控真实接口上核实，并记录测试目标、日期、操作 ID、前后结果（全部脱敏）。不允许把正式客户伪装成“测试名单”。

若服务无沙箱/专用测试账号，不能偷偷发送生产订单换取 PASS。报告应列为未执行；只有用户额外明确授权真实业务小批试用时才可另行验证，不在本文授权范围内。若决定仅使用已验证能力，则其它未验证能力必须在配置和 UI 上明确禁用，报告限定放行范围，不能宣称全功能通过。

### 5.6 投产前检查与保守启用

- [ ] 核对正式目标 file id、日期、账号、platform origin、并发和来源配置，避免测试配置误指正式表或旧目标。
- [ ] 备份当前配置/ledger/journal；恢复演练确认能读取备份，但未知远端写入后禁止仅回滚本地账本再重传。
- [ ] 实际待运行批次没有未处理的同范围阻断，跨范围记录可见、可核对；不得删除记录或清空目录来“通过验收”。
- [ ] 更新后首次使用先预览/预检，业务负责人核对摘要再执行；“验收通过”不等于免除业务确认。
- [ ] 如出现未知、重复、账本异常或回读不一致，停止新写入/下单，保留日志证据，只读核对再处置。

## 7. 最终放行硬门槛

- 没有真实凭据、订单数据或诊断业务文件被加入 Git；
- 验收报告已经记录所有未执行项和放行范围，并由业务负责人确认；风险签字不能替代未完成的 P0/P1 修复或硬门槛。

“通过”表示满足本文约定的证据和边界，不是零事故保证。未测试平台、未验证能力、正式账号权限/配置变化和后续代码变更不包含在通过结论内。
