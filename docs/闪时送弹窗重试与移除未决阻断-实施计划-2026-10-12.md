## 一、需求（用户原话与解读）

1. **弹窗模式加「最终确定」后自动重试**
   原话：「这个重试程序也需要加」。
   解读：把 2026-10-12 实机验证过的「人工式重试」并入生产代码。平台在点击
   「最终确定」后偶发内部错误驳回（`java.lang.IndexOutOfBoundsException`），
   表现为弹窗不关闭 + 顶部提示「操作失败」；再点一次「最终确定」即成功。
   程序应在驳回后原表单重试，最多 3 轮。实测数据见第二节。

2. **所有信息填写完成后，先等 0.5 秒再点「最终确定」**
   原话：「所有信息填写完成之后等过0.5s再点击确定，不要立刻点」。
   解读：填完（姓名/电话/名称/门牌号）后 `wait_for_timeout(500)` 再点第一次
   「最终确定」。动机推测：实测中 81/83 单的首点被驳回，疑似「填完立刻点」触发
   平台竞态；0.5s 静默预计能显著降低首点驳回率（待首轮实测确认）。

3. **删除「未决记录阻断」安全设计**
   原话：「直接跳过这个安全设计，后续如果需要改代码，先把这个安全设计给删了」。
   解读：删除未决订单日志（`sss_uncertain.json`）写入/跨运行阻断/只读核对/
   人工处置/批次互斥锁，以及配套 UI、接口、配置、测试与文档。
   **保留（明确不动）**：提交前后「站内对账」（下面第三节 3.5 有清单）——
   它对防重复的实际作用已在实机运行中验证（19 单站内已存在被跳过、收尾
   102/102 确认、0 重复），未决日志只是额外的「跨运行阻断」层。

## 二、实机验证结论（2026-10-12 上午，真实账号 102 单）

运行方式：生产代码路径（`run_sss_job`，浏览器表单模式）+ 驱动脚本
`/tmp/v365_run/drive_run.py`，仅猴补丁两点：① 登录等待用户手动完成（测试
台架专用，**不移植**）；② `_ui_click` 注入重试包装器（**这就是要移植的**）。
用户在场配合登录。

| 目标订单 | 102 单（午餐 80 + 晚餐 22） |
| 下单前站内对账 | 19 单站内已存在（早前运行创建）→ 跳过；83 单提交 |

**结论：重试机制有效且无副作用（0 重复）。** 另注意：83/83 单都被先标成
「提交结果未知」，原因统一是下面 2.3 的恢复检查缺陷（非真实未知），最终由
收尾对账救回。

### 2.2 平台错误形态

- 文案：`操作失败，java.lang.IndexOutOfBoundsException: Index: 0, Size: 0`
  （浅色提示框、页面顶部居中，antd message 样式，无按钮）。
- 已停 2026-10-09 排查记录（`docs/闪时送周期失败与序号跳号排查-2026-10-09.md`）：
  这是平台对建单节奏的快速驳回（每个请求仍消耗一个平台序号），不是客户端
  可修复的数据错误。
- 人工与脚本均验证：驳回后**原表单再点一次「最终确定」即成功**（表单数据不丢失、
  无需重新填写）。

### 2.3 实机中发现的既有缺陷（本次一并修）

- 现象：83/83 单打印
  `提交结果未知：弹窗收场后「创建订单」按钮未恢复（Error），无法确认订单状态`。
- 根因：`app/sss.py::_ui_wait_modal_closed` 的恢复检查直接用
  `page.get_by_text("创建订单")`（未收窄），页面同时存在导航按钮与弹窗标题残留
  → 多匹配 → Playwright strict mode 直接抛 `Error`（不是超时；日志里类型名正是
  `Error`）。本地最小复现验证：多匹配 + `wait_for(state="visible")` → 
  `Error: strict mode violation`；加 `.first` 即通过。
- 影响：所有真实成功单都被先分类为「结果未知」，日志噪音大（靠对账兜底没造成
  数据问题）。删除未决阻断后此误报仍会污染结果统计，必须修。
- 修复方向：改用 `_find_by_candidates`（内部收窄 `.first` 且带轮询），或最少加 `.first`。

### 2.4 实测验证过的重试逻辑（将移植进生产代码）

来源：`/tmp/v365_run/drive_run.py`（/tmp 重启可能被清，故原文照录）：

```python
_real_click2 = sss._ui_click


def retrying_click(page, step, timeout_ms, desc, **kwargs):
    """复刻人工动作：最终确定被平台内部错误驳回时，点掉报错框并原表单重试（≤3 次）。"""
    if desc != "点击最终确定":
        return _real_click2(page, step, timeout_ms, desc, **kwargs)
    for round_no in range(3):
        _real_click2(page, step, timeout_ms, desc, **kwargs)
        settled = False
        deadline = time.time() + 5
        while time.time() < deadline:
            if not page.locator(".ant-modal-mask:visible").count():
                settled = True
                break
            time.sleep(0.3)
        if settled:
            if round_no:
                log(f"第 {round_no + 1} 次点击后下单成功（人工式重试生效）")
            return
        try:
            err_btn = page.locator(".ant-modal-footer .ant-btn-primary:visible").last
            err_btn.click(timeout=3000)
            log(f"平台驳回（第 {round_no + 1} 次），已点掉报错框，原表单重试…")
            page.wait_for_timeout(600)
        except Exception:
            return
    log("重试 3 次仍未成功，本单按结果未知交给对账")
```

关键参数（实测值，建议照抄为常量）：
- 判定收场：`.ant-modal-mask:visible` 的 `count() == 0`（查 5 秒，轮询间隔 0.3s）；
- 驳回后点击 `.ant-modal-footer .ant-btn-primary:visible` 的 **last**，等 600ms；
- 最多 3 轮；3 轮后放弃并交给收尾对账（`_ui_wait_modal_closed` 继续等 90s，仍
  不收场才按「结果未知」处理）。

**待首轮实测确认的一点**：报错提示是 antd message（无按钮），因此
`err_btn.click()` 实际点到的很可能是**创建订单弹窗自己的「确定」**（即重试点击
本身），而非「报错框的确定」。两种解读的净效果相同（再点一次确定）。实施时
请在**首次出现驳回时保存一份现场截图/HTML**（可复用
`automation._save_failure_snapshot`），以确认动作语义；无论哪种，请先照抄上面的
点击序列保持与实测一致，再按证据微调。

### 3.5 新增/修改：重试 + 0.5s + 恢复检查修复（`app/sss.py`）

建议常量化：

```python
_UI_FINAL_CONFIRM_DELAY_S = 0.5      # 填完所有信息→首次点击的静默（用户要求）
_UI_FINAL_CONFIRM_ATTEMPTS = 3       # 驳回后最多点击轮数（实测值）
_UI_REJECT_SETTLE_WINDOW_S = 5.0     # 单轮点击后等收场的观察窗（实测值）
_UI_REJECT_RETRY_PAUSE_MS = 600      # 驳回后到下一轮点击的间隔（实测值）
```

`_ui_create_order` 第 7-8 步（L692-696）替换为：

```python
    # 7. 全部字段填完后先静默 0.5s 再点（用户要求；首点驳回疑似与点击过快有关）
    page.wait_for_timeout(int(_UI_FINAL_CONFIRM_DELAY_S * 1000))

    # 8. 最终确定 + 平台驳回重试（≤3 轮；逻辑照抄 2.4 实测版）
    final_step = step("最终确定")
    for attempt in range(_UI_FINAL_CONFIRM_ATTEMPTS):
        _ui_click(page, final_step, _UI_FINAL_CONFIRM_TIMEOUT_MS, "点击最终确定")
        if _ui_wait_mask_hidden(page, _UI_REJECT_SETTLE_WINDOW_S):  # 新增小工具
            if attempt:
                _emit(callback, f"第 {attempt + 1} 次点击「最终确定」后弹窗收场"
                                "（平台驳回重试生效）")
            break
        _emit(callback, f"平台驳回（第 {attempt + 1} 次），点掉报错后原表单重试…")
        try:
            page.locator(".ant-modal-footer .ant-btn-primary:visible").last.click(
                timeout=3000)
        except Exception:  # noqa: BLE001 - 点不到就交给收尾等待判定
```

## 五、风险与注意

- **移除未决阻断后的重复下单窗口**：若上次运行在「POST 已发出但结果未知」时被
  杀进程，下一次运行不再被阻断；防重复只剩「下单前站内对账」。站内列表存在
  数分钟级可见性延迟（2026-09-13 记录），紧接重跑可能重复提交少量订单。
  这是用户明确接受的设计取舍（原话「直接跳过这个安全设计」），如实留档。
- 批次互斥锁随日志一并删除后，跨进程并发防护消失；应用内并发仍由 bridge 的
  操作协调器（单一任务槽）挡住，单实例使用无影响。
- 重试会对同一单多次点「最终确定」（每轮最多 2 次点击：点击 + 驳回后点击）。
  实测 102 单 0 重复；平台对快速重复提交本身会快速驳回（见 2026-10-09 记录）。
- 用户数据目录里的遗留文件（`~/.config/yikou-light-food/sss_uncertain.json` 及
  `.bak-20261012-0810`、`.lock`、`.review.json` 等）在新版本中不再被读写；
  建议留档一段时间后再手工清理，不自动删除。
- 调试期往 `.venv` 装过 `ddddocr`（验证码 OCR 实验，未采用、未进 requirements.txt），
  可按需 `pip uninstall ddddocr` 清理。
- 本次 102 单实跑是用户授权下的真实下单（全部站内确认）；后续任何真实平台
  复测仍需用户在场配合登录，避免触发验证码风控升级。
