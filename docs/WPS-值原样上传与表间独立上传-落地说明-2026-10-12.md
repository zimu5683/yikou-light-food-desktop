## 1. 落地清单（需求 → 桌面端代码）

| 需求 | 桌面端落点 |
|---|---|
| 写进去、读回来、显示出来是同一个值 | 读：`KdocsCli.read_grid` 优先取 `originalCellValue`（`_read_cell_text` / `cell_value_text`）；写：`text_cell_formula` 让纯数字按文本写 |
| 电话不做位数校验、不截断、不改写 | 全链路保持原样：`person_key` / `normalize_phone` 只**丢符号留数字**（空格、连字符、`+86`、前导 0 都不做语义处理），没有任何位数判断 |
| 用值匹配，不用显示文本 | 人键一律 `person_key(name, phone)`；`_is_rate_…` 无关。读层修好后，`build_plan` / `read_person_rows` / `wps_recovery` / `sss_import` 全部自动受益（都只吃 `read_grid`） |
| 「云端已有同名的人（电话不同）」只在值真的不同时提醒 | 该提醒本来就按人键判定；读层不再把显示值当值，因此不再因科学计数误报 |
| 重复同步幂等 | 本次未改幂等逻辑（账本 + 计划口径）；值一致 → `needs_write` 为假 → 不写格子，回归已锁（`test_sync_is_idempotent_for_text_phone_values`） |
| 一张表失败/不确定不牵连别的表 | 闸门本来就按「同日期 + 同表」（`_guard_block_reason` → `journal.blocking_operations`），逐表 `continue`；本次补上**未预期异常**的逐表兜底（`_abort_sheet`） |
| 汇总逐表给出结论 | 已有（`result["sheets"]` 逐表状态 + 桥接层逐行日志）；本次新增的兜底也走同一口径（`status="failed"` + `uncertain=True`） |

## 2. 关键实现（`app/wps_cloud.py`）

1. **读**：`read_grid` / `read_cell_format` 改用 `_read_cell_text(cell)` ——
   `originalCellValue` 非空时取它（数值型会经 `cell_value_text` 去掉 `.0`），
   否则退回 `cellText`（老响应/无原值字段时行为与改动前一致）。
2. **写**：新客户行的电话格走 `text_cell_formula(change.phone)`：纯数字加前置
   单引号（电子表格的"按文本存"约定），显示与回读都保持原样；带空格/连字符/`+86`
   的形态原样写。姓名/地址/餐种等非数字文本不受影响（回读校验、公式回读均未改）。
3. **逐表兜底**：`_apply_plan_locked` 的逐表循环包一层 `try/except Exception`，
   命中时 `_abort_sheet` 把该表记成「结果未知」（`uncertain=True`，不回滚也不猜），
   日志提示去「云同步恢复」核对，**整批继续**。

## 3. 与需求的刻意取舍

- **不做号码清洗**：`person_key` 只丢非数字字符。`159 6789 9961` 与 `159678999961`
  在**云端值**上仍是两种写法（显示与回读都忠实），需要人工统一时由数据侧处理，
  程序不猜。
- **兜底按 uncertain 而不是 failed**：异常可能发生在任何一个云端请求之后，本地
  证明不了"一个格子都没写"；记错方向的代价不对称（可能重复加餐）。按需求第 4 条
  "同类风险各自独立暴露"，这张表自己进恢复卡片，不影响别的表。
- **已损坏的线上格子救不回来**：`cellText = 1.59679E+11` 只剩 6 位有效数字，
  任何解析都还原不出 `159678999961`。做法是不让它再产生（写文本 + 读原值），
  存量按需求 §8 人工改回文本。
