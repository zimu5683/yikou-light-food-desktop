# 一口轻食桌面端与手机/服务端功能差异及补齐计划

**文档日期：** 2026-10-07  
**桌面端项目：** `yikou-light-food-desktop`，当前版本 `3.5.1`  
**手机/服务端项目：** `yikou-light-food-server`，当前版本 `3.6.15`

本文用于说明两个本地项目之间的功能差异，并作为后续桌面端补齐工作的实施依据。比较重点是用户可感知的业务行为、安全边界和运行能力，不是简单的文件逐行同步。

**审计基线：** 桌面端 HEAD `ef936a1`（2026-09-16），服务端 HEAD `cbe6401`（2026-09-27）。本文基于本地源码、提交记录、文档与测试定义的静态核对；本次没有实际登录平台、写入 WPS、创建订单或重新运行全部测试。版本号指本地代码版本，不代表已联网核实远端最新 Release。

**阅读约定：** 文中以 `server/` 开头的路径指 `yikou-light-food-server` 仓库，以未加前缀的业务路径通常指桌面仓库。源码行号仅适用于本次基线，后续修改后应按方法名定位。

---

## 1. 结论先行

手机/服务端相对于桌面端，真正需要回移的功能主要有四类：

1. **WPS 云同步的数据正确性**：总餐次增量累加、保护协作者写入的 `0`、支持同一客户多行、批次日期闸门。
2. **WPS 云同步的预览和恢复安全机制**：预览令牌、上下文校验、计划/执行统计、部分失败恢复。
3. **闪时送未决订单安全机制**：持久化 journal、跨重启阻断、只读核对、人工审计解除，防止重复下单。
4. **统一操作状态、并发互斥和异常恢复**：避免任务、WPS 上传、更新操作互相覆盖，或前端断线后丢失状态。

建议补齐的增强包括：

- 管理后台 WAF 登录预热和 HTTP 403 重试；
- 闪时送时间窗对账、8 路并发、30 秒读取超时和吞吐统计；
- 前端对失败、未知、恢复中状态的明确展示。

手机端新增的网页账号审批、Android APK、Termux、Cloudflare Tunnel、手机日志浮窗等功能，不属于桌面端必须补齐的功能。桌面端还应继续保留自己的 Windows/macOS/Linux 打包、pywebview、Playwright fallback 和桌面自动更新能力。

## 3. 功能差异矩阵

| 功能领域 | 桌面端 `3.5.1` | 手机/服务端 `3.6.15` | 结论 |
|---|---|---|---|
| 管理后台订单处理 | 已有纯接口和浏览器备用模式 | 主要做了领域拆分和稳定性增强 | 保留桌面实现，做回归验证 |
| WPS 总餐次 | 本地餐次直接覆盖云端总餐次 | 云端原值 + 本批未同步增量 | **必须补齐** |

| 统一操作互斥 | 主要只有任务线程锁 | 订单、闪时送、WPS、更新统一协调 | 建议补齐 |
| 操作状态查询 | `worker_alive()` 和简单状态 | `operation_id`、阶段、冲突、最近结果 | 建议补齐 |
| WAF 登录 | 403 后提示切浏览器 | WAF 预热、新 Session 重试 | 建议补齐 |
| 网页账号审批 | 无 | 注册、审批、邀请码、角色 | 桌面端不需要 |
| Android APK | 无 | Chaquopy、Kotlin、内置 kdocs-cli | 桌面端不需要 |
| 手机日志交互 | 桌面日志面板 | 浮动按钮、水波层、软键盘适配 | 不整体移植 |
| Windows/macOS/Linux 打包 | 已有 | 服务端已删除 | 必须保留桌面实现 |

## 4. P0：WPS 数据正确性

### 4.1 总餐次改为增量累加

桌面端 README 仍然记录旧规则：

```text
README.md:118    总餐次写成与本地「餐次」一致
README.md:127    总餐次写的是绝对值而不是累加值
```

服务端在 `3.6.11` 中修正为：

```text
本批增量 = 本地本批餐次 - 账本中已经同步的本批餐次
云端新总餐次 = 云端当前总餐次 + 本批增量
```

例如：

```text
云端原值：5
本地本批：6
第一次上传：5 → 11
重复上传：增量为 0，不再写入
```

服务端参考：

```text
app/wps/planner.py
app/wps/ledger.py
app/wps/reader.py
app/wps/executor.py
```

桌面端对应：

```text
app/wps_cloud.py
```

要求：

- 兼容旧账本中的整数或旧版 `meals` 字段；
- 新账本按“批次 + 客户 + 行槽位”记录；
- 重复上传不能翻倍；
- 云端回读校验成功后才更新账本；
- 测试模式不能污染正式账本。

### 4.2 保护协作者写入的 `0`

日期格规则应改为：

```text
空值        → 可以写入 1
已有 1      → 保持 1
已有 0      → 只读，不覆盖
其它非空值  → 只读，不覆盖
```

原因是闪时送名单按日期格为 `1` 的客户下单。协作者写入 `0` 通常表示当天不送，不能被同步程序改成 `1`。

回读校验必须确认：

- 空值写入后为 `1`；
- 已有 `1` 仍为 `1`；
- 已有其它非空值与原值相同；
- 校验不通过时不能报告成功。

### 4.3 支持同一客户多行

同一个人一天可能有两行，例如一晚两单或两份餐拆成两行。正确行为是：

```text
本地同一客户两行
→ 云端同一客户保留两行
→ 两行分别写入日期格和餐次
→ 账本按槽位记录
```

不能继续只使用：

```text
(姓名, 电话) → 行号
```

应使用类似：

```text
(姓名, 电话, slot) → 云端行号
```

### 4.4 增加批次日期闸门

上传前检查本地表的星期/日期标记是否对应目标日期。以下情况必须整批拒绝：

- 本地批次日期与目标日期不一致；
- 目标日期无法可靠解析；
- 子表日期信息不完整；
- 运行时间窗口与目标日期推导结果矛盾。

拒绝时必须保证：

```text
云端写请求次数 = 0
账本更新 = 0
新行插入 = 0
```

## 5. P0：WPS 预览、上传和恢复安全

### 5.1 预览必须产生一次性 `preview_id`

桌面端当前接口是：

```text
wps_preview()
wps_upload()
```

服务端已改为：

```text
wps_preview() -> preview_id
wps_upload(preview_id)
```

参考实现：

```text
server/app/api/bridge.py:3846
server/app/api/bridge.py:3943
server/app/api/preview.py
```

上传前需要校验：

- `preview_id` 存在且未过期；
- 本地 Excel SHA-256 未变化；
- WPS 目标表配置未变化；
- 测试/正式模式未变化；
- 目标日期和地址排序配置未变化；
- 预览没有被成功消费过。

以下情况统一拒绝上传：

```text
没有预览
预览过期
本地文件已变化
配置或目标表已变化
预览已消费
预览属于另一轮操作
```

### 5.2 分离计划统计和执行统计

预览使用 `planned_summary`：

```text
计划更新行数
计划新增行数
计划不变行数
计划跳过行数
计划告警数量
```

上传使用 `execution_summary`：

```text
成功表数量
失败表数量
未知表数量
跳过表数量
实际成功行数
实际失败行数
是否能证明零写入
下一步动作
```

禁止使用“计划更新 100 行”代表“实际已经成功写入 100 行”。

### 5.3 WPS 部分失败进入恢复状态

服务端参考：

```text
server/app/wps/recovery.py
server/app/api/bridge.py:2934  wps_recovery_status()
server/app/api/bridge.py:2994  wps_recovery_resolve()
```

桌面端需要增加：

1. 上传开始前保存本地操作账本；
2. 每张表记录执行状态；
3. 异常时区分成功、失败和未知；
4. 只读恢复状态不修改云端；
5. 人工选择恢复动作；
6. 恢复动作二次确认；
7. 写入本地审计；
8. 已处理恢复操作重复提交时幂等。

桌面端是单用户程序，可以不引入服务端角色权限，但不能省略明确确认和审计。

**恢复不是自动补写云端。** 应对照服务端最终契约保留 `cloud_verified`、`cloud_untouched`、`retire_guarded`、`keep` 四类动作；处置入口本身不写云端。`retire_guarded` 只是让旧任务退出全局待处理队列，仍保留同日期、同目标表的重放阻断，不能理解为“允许再次上传”。`cloud_verified` 和 `cloud_untouched` 必须分别以云端只读核验证据确认已完成或未开始，不能仅凭用户勾选就放行。

## 6. P0：闪时送未决订单安全

这是两个项目之间最重要的安全差异。

桌面端已有“至少一次提交 + 下单后对账”，但没有跨运行持久化的权威未决记录。相关代码主要在：

```text
app/sss.py
app/bridge.py
```

服务端新增参考：

```text
server/app/ordering/uncertain.py
server/app/ordering/reconcile.py
server/app/ordering/submission.py
server/app/api/bridge.py:923
server/app/api/bridge.py:1213
server/app/api/bridge.py:1303
```

### 6.1 建立 authoritative journal

只要下单 POST 已发出，但客户端没有拿到确定响应，就必须记录为：

```text
已发送但结果未知 / unresolved
```

至少记录：

```text
journal_id
批次键
账号
平台 origin
目标送达日期
姓名
手机号脱敏值
地址和门牌
商品
请求指纹
发送时间
异常原因
状态
```

### 6.2 跨运行阻断

同一批次再次运行时，如果仍存在 `unresolved`：

```text
不允许自动发送 POST
不允许通过重启程序绕过
不允许通过再次点击“开始下单”绕过
必须进入只读核对或人工处置
```

服务端当前批次键为 `送达日|规范化账号`。**名单来源不得作为隔离阻断的键**：切换 `wps/excel` 不能解除同一批次的未决记录。平台 origin、权威 journal 位置及锁目录由其它身份/位置闸门校验，不应简单拼成可以随配置切换的新文件名。

切换账号、网址、日期或名单来源时，不能把旧记录误认为当前批次，也不能静默丢弃旧记录。

还需移植 URL/账号规范化、跨作用域记录检查和权威位置守卫。参考 `server/app/integrations/sss_url.py`、`server/app/ordering/uncertain.py` 及 `test_sss_url_authority_guard.py`、`test_sss_authority_location_guard.py`。尾点域名、等价 URL 写法、空白/全角账号、切换 Excel 路径或 journal 路径都不应绕过阻断。

### 6.3 必须同时覆盖两条提交路径

桌面端同时支持：

```text
纯 HTTP API 模式
Playwright 浏览器备用模式
```

两条路径都必须接入同一套：

```text
提交前闸门
提交后记录
异常归类
只读对账
journal 解析
人工处置
```

## 7. P1：闪时送只读核对和人工处置

### 7.1 只读核对入口

增加：

```text
start_sss_review(payload)
```

只允许登录、查询订单、查询目标时间窗和保存核对快照，严禁发**创建订单 POST**或自动补发。登录本身可能使用 POST，“只读”指对远端订单不产生写入副作用。

服务端核对过程中会把可靠匹配到的未决记录自动标记为本地 `resolved`，因此这不是“本地文件完全不变”的入口。移植时保留这一行为及其原子落盘校验；对仍然缺失或无法确认的记录，只生成证据，不自动解除重发阻断。该入口不应因 `remember` 参数保存密码或修改配置。

建议分类：

```text
station_confirmed       站内已找到对应订单
station_missing         站内时间窗内确认没有订单
station_found_other_day 找到相似订单但日期不同
scan_failed             读取失败，无法判定
```

“查询失败”绝不能当成“站内没有订单”。

### 7.2 未决记录列表

增加：

```text
sss_uncertain_records()
```

返回内容应脱敏：

- 手机号只显示前 3 位和后 4 位；
- 不返回密码、token 或完整请求体；
- 返回状态、目标日期、地址、错误原因和下一步建议。

journal 损坏时返回 `journal_unreadable`，不能返回空列表伪装成“没有未决记录”。

### 7.3 人工处置入口

增加：

```text
sss_uncertain_resolve(payload)
```

建议支持：

```text
station_present
    站内已有订单，标记本地记录为已确认

station_absent
    人工确认站内没有订单，解除阻断，允许后续重跑

keep
    保持阻断，不改 journal（服务端当前 keep 为 no-op）
```

`station_absent` 必须同时满足：

- 有新鲜只读核对快照；
- 快照未过期；
- journal 指纹未变化；
- 所选记录全部参与核对；
- 全部记录均为 `station_missing`；
- 用户确认本次不发送 POST；
- 用户填写人工备注。

按当前服务端实现，核对证据有效期为 **600 秒**；`confirm` 必须与 `decision` 一致，备注至少 **4 个字符**，并显式传递所选 `record_ids`。成功处置仅更新本地 journal/审计，不联网、不创建订单。`station_absent` 解除后，用户下一次主动启动才可能实际发单，确认文案必须说明这一后果。

## 8. P1：统一操作状态和并发互斥

桌面端的 `_worker_lock` 主要保护订单/闪时送任务，不能完整覆盖 WPS 上传、WPS 授权、WPS 恢复、只读核对和更新安装。

服务端参考：

```text
server/app/api/operation.py
```

建议增加 `OperationCoordinator`，提供：

```text
try_reserve(mode)
update(operation_id, phase=...)
finish(operation_id, status=...)
operation_status(operation_id)
```

覆盖模式：

```text
order
sss
sss_review
wps_preview
wps_upload
wps_authorize
wps_recovery_resolve
check_update
install_update
```

统一状态至少包括：

```text
operation_id
mode
status
active
phase
reason
next_action
summary
started_at
finished_at
```

并发冲突应立即返回，不应该让前端请求线程长时间等待。

## 9. P1：闪时送对账提速和 WAF 登录稳定性

### 9.1 对账和并发

桌面端当前配置：

```text
sss_max_workers = 4
sss_read_timeout_s = 20.0
```

服务端 `3.6.15` 已调整为：

```text
sss_max_workers = 8
sss_read_timeout_s = 30.0
```

不能只改默认值，还需要移植：

1. 按目标送达日构造时间窗；
2. 服务端时间筛选；

旧桌面版本没有完整的跨运行 journal。升级时不能伪造“历史记录已经安全”。如果用户刚刚从旧版发生过超时或异常下单，应提示先人工核对站内订单；不能通过删除配置文件默认解除新机制。

## 14. 验收标准

### 14.1 WPS

必须覆盖：

```text
云端 5 + 本地 6 = 11
同一批重复上传 = 0 写入
协作者日期格为 0 = 保持 0
同一客户两行 = 云端两行
星期不匹配 = 0 次云端写请求
目标日期列不存在 = 0 次写入
排序范围异常 = 新插入行回滚
本地文件变化后旧 preview_id = 拒绝上传
云端部分失败 = 进入恢复态
未知结果 = 不自动重试
恢复操作重复提交 = 幂等
```

### 14.2 闪时送

必须覆盖：

```text
POST 超时后生成 unresolved journal
程序重启后同批次继续阻断
journal 损坏时 fail-closed
只读核对不发送 POST
找到站内订单后可以标记 confirmed
站内明确没有订单后才能解除阻断
核对过期不能解除
journal 指纹变化不能解除
并发运行只能有一个批次
纯 HTTP 和 Playwright 两条路径都能记录未决
```

### 14.3 前后端契约

需要新增或更新：

- Bridge API surface 测试；
- WPS preview/upload 契约测试；
- WPS recovery 契约测试；
- 闪时送 uncertain 契约测试；
- operation conflict 测试；
- 前端按钮禁用条件测试；
- 错误状态和下一步动作测试；
- TypeScript 类型与 Python 返回值测试。

### 14.4 桌面平台

至少验证 Windows、macOS、Linux 的 pywebview、内置 Chromium、Playwright fallback、系统密钥环、WPS CLI、桌面自动更新和回滚。
