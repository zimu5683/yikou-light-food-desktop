### D01 多行客户排序后槽位身份错配

排查记录把该问题记成一条，本轮复现把它拆成三个相对独立的点：**D01**（行身份错配：旧餐次被覆盖、新行漏写）、**D01-b**（错位被观测到却仍产生成功结论）、**D01-c**（回读校验不含地址列）。

**根因**

- D01：执行器按「槽位序号 → 这个人的第 N 个物理行」定位（`position = max(1, int(change.slot or 1)) - 1; row = rows[position] ...`，排查记录位置 `app/wps_cloud.py:2823`）。排序后同一客户各行的先后由地址排序键决定，槽位与原始行身份脱钩；预测（`plan.final_rows`）与实际不一致时只打一条 WARN（文案还断言"不影响数据正确性"）随后仍按错位行号写入。
- D01-b：`plan.sort_mismatch = True` 只是诊断字段，不参与状态判定；`status` 照发 `"ok"`、`failed` 不增加，桥接层据此把整批判成成功。`grep -rn sort_mismatch` 全仓只有 `app/wps_cloud.py` 与 `app/wps_preview.py`（仅透出到预览），无任何门控。
- D01-c：回读校验的 `verify_cols` 只有目标列 / 总餐次 / 姓名 / 已出餐 / 剩余餐，没有地址列——而"变更地址 ≠ 落表地址"正是行身份错位在每个场景都成立的信号。

**修法**（`app/wps_cloud.py`）

1. 计划侧在排序前给每条 `Change` 记下可复原的身份：`address_in_sheet` / `group_index` / `group_total`（`app/wps_cloud.py:239-241`，计划内分配见 `:2268-2324`）。
2. 执行器第 5 步改为按「人 + 地址组 + 组内序号」定位（`app/wps_cloud.py:3404-3418`）；组内行数或序位对不上 = 证明不了"还是原来那一行"，整表停止写入并记 `status="failed"` + `uncertain=True`（同段 `unlocated` 分支，`:3435-3447`，文案为"排序后按「地址 + 组内序号」定位不到这些变更（…），已停止写入。表已重排，请重新上传（重复执行安全）"）。
3. 回读校验加入地址列（`app/wps_cloud.py:3528-3531`、比对逻辑 `:3572-3578`）；地址不符 → `problems` → `status="verify_failed"` + `mark("uncertain")`（`:3597-3604`）。
4. `sort_mismatch` 降级为纯诊断字段，不再落在成功口径里；删除"不影响数据正确性"式文案。

**新增/修改的测试**（`tests/test_wps_cloud.py`）

- 新增：`test_多行客户排序后槽位身份不错配`、`test_多行客户排序后增量写回原行`、`test_排序后地址回读不符必须失败`、`test_同地址组内新增行排在既有行之后`、`test_回读地址与变更不符时校验失败`。
- 既有用例 `test_actual_sort_result_wins_over_prediction`（`tests/test_wps_cloud.py:963`）按新语义最小更新：docstring 重写为"`plan.final_rows` 只是预测/诊断、写入按地址组定位并逐行核对地址"，并**追加**一条断言"落表行的地址列 == 变更地址"（是加强，不是放宽）。

**复核证据**

**残留风险**

1. 身份定位依赖「云端 range-sort 对等键稳定、同组既有行在前新行在后」这一既有假设（`sort_key_value`）。复核给出实测反例（E5）：把替身排序改成"等键不保序"（同一人同地址两行互换）后，+2 落到原本 20 餐那行、20 被覆盖成 12、合计 24≠34，而 `status='ok'`（仅一条 WARN）——即"回读总餐次能兜住互换"的说法**不成立**（地址相同则无法区分）。真实平台排序稳定性无法离线验证。
2. fail-closed 代价：定位不到时整表不写，但此前插入的新行**不回滚**（`_verify_inserted_block` 对"同一人多行"判负，属既有行为），云端会留一条只有姓名/地址的残行，需要人工重传；残行在下次上传时能否被正确归位未验证。
3. 表中没有地址列时身份退化为"这个人的第 N 行"（与修复前一致），此类仍可能发生同型错配。
4. 地址比对走 `_address_key` 归一化（忽略空白与大小写）：同一行地址被改成同义写法（B1/b1）不会被发现（不影响行身份）。
5. 新字段（`address_in_sheet` / `group_index` / `group_total`）未加入 `app/wps_preview.py` 的指纹白名单（有意保持最小改动），"身份字段单独变化"不会被指纹识别。

### D02 补单重跑改变行序，旧订单被当作新槽位（**部分修复**）

**根因**：增量计算把本地第 i 行直接当第 i 个槽位、`prev = prev_slots[slot-1]` 按位置取账本锚点、按位置绑定云端行，全程不看订单身份（`CloudOrder.order_no` 当时无消费点；订单处理按 W 编号从大到小写行，正常补单就会改变组内行序）。

**修法**（`app/wps_cloud.py`，与 D03/D04 共用同一批改动）

1. 槽位身份：`Change` 记 `order_no`；账本条目在 `slots` 之外并列 `orders`（槽位订单号）与 `positions`（槽位在云端这个人的第几行）。读取层 `SyncLedger.synced_orders`（`:1031`）、`synced_positions`（`:1047`）；校验层（`:776-830`）要求 `orders`/`positions` 存在时与 `slots` 等长，否则 `LedgerCorruptError`（失败关闭）。
2. 规划侧 `_slots_by_identity`（`:1733-1785`）：按账本订单号把本地行放回**槽位下标**；账本有身份而本地缺行的槽位留 `None`（不压缩——D03）；带号但对不上账本的新单放进"账本没有身份"的位置，匿名行只能填剩余空位。
3. 失败关闭判据：`_identityless_pairing_double_counts`（`:1670`）与 `_anonymous_pairing_double_counts`（`:1696-1730`）命中时"这个人的云端行一个都不动"，在预览/日志里给明确警告（`:2036-2067`）。
4. 槽位 → 云端物理行：账本记过 `positions` 就按它取行（计划代码 `:2109-2123`），旧账本/本批新槽位才退回按数组位置配对。
5. 旧账本兜底：本批按位置配对时**仍写订单号与位置进账本**，供下一批核对；noop 批次也补记身份（`_identity_backfill_keys` `:2631`，调用点 `:3457`）。

### D03 本地行数减少时丢失最后一个已同步槽位

**根因**：`max_slot = max([0, *by_slot, *range(len(old_slots or []))])` 把 0-based 的 `range` 与 1-based 的槽位混用，本地行数少于旧槽位数时最后一个旧槽位不被纳入，防重复锚点随 `slots` 一起被截掉。

**修法**：改为 1-based `range(1, len(old_slots or []) + 1)`（并同步覆盖 `old_orders`，`app/wps_cloud.py:2713-2714`）；未变更槽位沿用旧锚点与旧身份（`:2726-2730`）；本地行数减少且缺的是中间行时，按**槽位下标**对齐、缺行槽位留空且跳过（`_slots_by_identity` + 主循环 `if order is None: … continue`，`:2078-2091`），并在计划警告里说明"本地行回来后按订单身份核对，不会重复加餐"。

**新增/修改的测试**（`tests/test_wps_cloud.py`）：首轮 `test_账本本地行数减少时保留末尾旧槽位`、`test_本地行数减少再恢复不重复加餐`、`test_本地行数减少时journal意图与磁盘账本一致`；二轮返工追加 `test_按槽位身份对齐缺行的槽位留空不压缩`、`test_本地行数减少丢中间行时按槽位下标对齐`、`test_本地行数减少丢第一行时不动云端那一行`、`test_本地行数减少丢中间行时更新写在正确的物理行上`、`test_本地订单列为空的行仍按剩下的空位配对`。

**复核证据**

- 独立复核记录（两轮）：结论 **fixed**。第二轮复核用"只回退 `_slots_by_identity` 与其调用点"的副本对照：`4 failed, 129 passed`，失败的正是对齐用例（判别力成立）；随机不变量脚本（3000 组、含排序开/关、随机丢首/中/末行）0 次违反。

**残留风险**（复核给出，均未消除）

1. 旧账本（**有 slots、无 orders**）下"本地行数减少但缺的不是最后一行"仍会永久多入账，且只有警告、没有拦截：复核探针 P1 实测 7→12；随机量化（1500 组）显示缺非末尾行的 762 组里合计错 **446 组（29.7%）**，缺行只在末尾的 370 组全对。该数字在 HEAD 与修复前副本上完全相同——属既有分支、非本轮引入；因为旧账本里没有任何每槽位归因，无法区分"保留的是哪一行"。

### D04 云端不扣减，但账本同步基准倒退

**根因**：规划把负增量截为 0（`if added < 0: … added = 0`，故意的"云端不扣减"保护），记账却把**本地值** `change.local_meals` 直接写成"本批已同步量"——云端仍持有原入账，防重复基准却降低，本地回到原值时按差额再加一遍。

**修法**：`app/wps_cloud.py:2723-2724` 改为 `slots.append(int(change.ledger_prev or 0) + (int(change.total_after) - int(change.total_before)))`，即"账本旧值 + 本次实际写入云端的增量"；负增量被截 0 时锚点保持不动。文档串口径同步改为"本批在云端**已入账**的累计量"（`_ledger_entries` docstring）；条目 `local`（=sum(slots)）随之变为"已同步量"（与 `_entry_merge_key` 的合并权重语义一致；`synced_local`/`synced_meals`/`synced_total` 在 `app/` 内无消费点，已 grep 确认）。

**新增/修改的测试**（`tests/test_wps_cloud.py`）：`test_负增量被截时账本基准不倒退`、`test_本地先减后恢复不重复加餐`（另与 D02/D03 用例组共用场景）。

**复核证据**

- 独立复核记录：结论 **fixed**。判别力：在 HEAD 副本上跑同组 `-k` → `9 failed`，D04 端到端用例以 `At index 0 diff: 4 != 6` 失败（即"账本锚点不能随本地减少而倒退"确实能抓到旧行为）；自写对抗脚本 A～E 全过；360 次重放（6 种子 × 60 步随机本地配置）三个不变量（云端只增不减、账本 slots 之和 == 云端合计、重放见过的配置一个餐次都不加）全部成立。

### D10 重登后自动补发已发送但结果未知的订单

**根因**：重登分支只按"站内列表可见性"决定补发范围（`current = after_login.missing` → `submit_round(current)`），没有扣除本轮已经发出、结果不可确认的任务；`first.uncertain` 只被记进 `all_errors` 并打了一行"不会直接重发"的日志，没有参与补发名单计算。对账天生滞后于建单，"重登后仍读不到"不能等价于"没建单"。

**修法**（`app/sss.py:2541-2569`）：`sent = set(first.succeeded) | {identifier for identifier, _ in first.uncertain}`；`withheld = after_login.missing ∩ sent`（只扣下、继续留在 `current` 走收尾对账与 `final.missing`，不能被当成"已完成"）；`resubmit = after_login.missing \ sent` 才调 `submit_round`；扣下时明确日志"…不会自动补发；如确未收到请人工处理"。明确登录拒绝（服务端未建单）与从未派发的任务不在 `sent` 里，仍走恢复流程。人工重试通道（decision_callback）保留为唯一重发出口。

**新增/修改的测试**（`tests/test_sss.py`）：`test_重登后不自动补发已发送但结果未知的任务`、`test_端到端_重登不会自动重发结果未知的已受理订单`。

**复核证据**

- 独立复核记录：结论 **fixed**。① 复现脚本 `--expect fixed` → EXIT=0：底线观测 `post_order=["张三","李四","李四"]`、站内 `{张三:1, 李四:1}` 共 2 单、`duplicate_count=0`；`--expect defect` → EXIT=1。② 失败前副本（精确反向替换的副本）→ 5 failed，D10 断言 `assert ['张三','李四','张三','李四'] == ['张三','李四','李四']`。③ 对抗台：超时+登录失效混合、4 单 3 路并发、重登后列表立刻可见、明确被拒（success=false）、只有未知单、补发轮再遇 401 —— 均符合期望；唯一反例"已受理却被判登录失效"在修复前副本上结果相同，属既有边界。

### D11 用请求分页大小判断结束，漏查第 2 页已有订单

**根因**：`_list_records` 只保留 `records` 与 `total`，把响应里的实际 `size`/`pages`/`current` 丢掉；`_list_pending_orders` 的结束判定两处都用**请求值** `page_size=100`（`len(page_records) < page_size`、`page_no * page_size >= total`）。服务端按 10 条/页返回时第 1 页后就 break，第 2 页真实订单永远看不到 → 把已有订单当缺失重复下单。
